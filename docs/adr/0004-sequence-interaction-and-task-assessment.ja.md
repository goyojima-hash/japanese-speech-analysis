# ADR-0004: Interaction拡張と項目別達成度処理の導入順序（旧案）

> 特定の設問・サンプル数を前提とする部分は採用しない。現在の汎用設計は [発話行為観測と項目別達成度の分離・検証](../task-assessment-shadow-design.ja.md) を参照。

**状態:** Proposed（実装・採用は未決定）

## 背景

InteractionのFact Moduleはすでに `jgrade_eval/interaction.py` と `fact_modules.py` に存在し、録音モード、設問有無、回答候補区間、対話表現候補をLLMなしで出す。ただし、現在のEvidenceは録音全体の文字起こしと音声区間時刻を別々に持ち、文字列と時刻を厳密に対応付けた区間別Transcriptは持たない。複数設問の連続録音で、候補回答の時刻があっても、その発話内容を設問へ安全に割り当てられるとは限らない。話者分離・学習者話者の確定もまだ一般には利用できない。

現行JudgeはCEFRと `task_rating` を同じ呼び出しで直接返す。APIとターミナルにはJudge入力と達成度集約の差がある。既存の５軸Fact、公開結果、CEFR協議を壊さず、発話行為の推定観測と設問固有の固定基準を分けて検証したい。Fact ModuleにLLMや評価責務を入れず、Judgeへ生音声も渡さない。

## 選択肢

| 案 | 利点 | 欠点・危険 |
| --- | --- | --- |
| A. Interactionを全面完成してから二段階評価 | 複数設問・対話録音まで一度に扱える | 話者分離、時刻付きTranscript、区間確定など大きな依存を先に抱え、採点分離の仮説検証が遅い。InteractionがJudge専用の下請けになりやすい |
| B. 二段階評価を先に全入力へ適用 | 日付確認の仮説を早く検証できる | 設問・回答対応が未確定な録音や試験官発話に誤適用する危険。５軸選択に設問情報が連動する構造も残る |
| C. Interactionと二段階評価を一体実装 | まとまった機能を一度に届けられる | 共通契約、録音分割、モデル出力、固定基準、API/CLIが同時に動き、原因切り分けと巻き戻しが難しい |
| D. 薄い共通契約の後、単一設問で二段階評価をshadow検証し、Interaction拡張を段階統合 | 仮説を早期に検証しつつ、複数設問への危険な適用を防げる。Interactionの独立性を維持できる | 段階的な互換アダプタと評価データ管理が必要。複数設問の正式採点までは時間がかかる |

## 推奨決定

**Dを推奨する。** ただし「二段階評価を先に実運用で採用する」という意味ではない。実験の順序と正式採用の順序を分ける。

1. **基盤・回帰の固定**: 現行API/CLI結果、Judge入力差、５軸の客観データ、モデル呼び出し回数を回帰テストで固定する。５軸の選択から独立した `TaskContext v1` を導入する。`prompt_id`、原文、承認された `task_type/rubric_id`、回答区間、対応状態、区間別Transcriptとその根拠を表現できるが、不明値は推測で埋めない。Interactionを無効にしても設問情報はJudge側で使える。
2. **評価仮説を小さく検証**: 「日付確認」など１種類の設問で、録音全体がその単一設問への回答と明示確認された例だけを対象に、Judge層で `TaskObservation`（AIによる行為の推定、根拠引用、不明）を作り、版管理された `TaskRubric`（LLMなしの決定的な変換）を適用する。`assessment_mode=off` を既定にし、`shadow` を明示選択した時だけ旧直接判定と並行比較する。旧 `task_rating` とCEFRを上書きしない。失敗・タイムアウトは旧経路へ影響させない。
3. **Interactionを独立に拡張**: 区間別文字起こし／時刻対応、録音モード、話者役割、人による候補区間・設問対応の確定を追加する。これは共通前処理・入力契約の能力であり、Interaction Fact Moduleはそれを読み取って客観Packetを出す。話者分離などのproviderは任意依存とし、失敗・未導入時に能力不足を明示する。５軸は互いに呼び合わない。
4. **複数設問へ統合**: `prompt_id`、学習者話者、回答の時刻とTranscriptが一致することを確認できる設問だけ二段階評価を実行する。候補だけ、時刻だけ、話者不明なら `insufficient_context`／要人手確認で保留する。録音レベルの従来CEFR推定は別に継続できる。設問別達成度をCEFRへ二重計上しない。
5. **正式採用の判定**: 開発用8組と別の凍結済み未使用データで、現行直接判定と同一条件比較をする。人手複数評価者との一致、誤陽性・誤陰性、◎○△×の順序誤差、保留率、設問なし／ASR誤り／複数話者での安全性、費用・遅延を事前基準で審査する。合格した設問型だけ明示的な新API版またはopt-inで採用する。

手順2と3は手順1の契約が固まった後なら、異なるファイル境界で並行開発してよい。ただし本番統合は手順4で行い、未完成の区間対応を理由に達成度を推測しない。

## 不変条件と回復

- ５軸FactはLLM・CEFR推定・達成度判定を行わず、必要な軸を単独選択できる。
- `TaskContext` はInteraction Packetの有無に依存しない。Interactionを外しても設問入力は失われない。
- 単一設問の確認済み回答以外は、時刻付き・話者付き・文字起こし付きの対応ができるまで新しい項目別達成度を保留する。
- 旧APIの公開 `task_rating` と `final_cefr_level`、ターミナルの既存表示は初期導入で変更しない。API/CLIの既存差は専用の互換性テストを通して別変更で整理する。
- `assessment_mode=off` で追加AI呼び出しなしの旧挙動に戻せる。観測モデル、ルーブリック版、入力来歴、比較結果は監査可能にする。
