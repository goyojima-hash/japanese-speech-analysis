# Interactionモジュール実装タスク（提案）

この順序で実装する。候補分割や話者分離を先にJudgeへ接続しない。

1. **Context契約と検証**
   - `AssessmentContext`、`Prompt`、`CandidateAnswerSegment`、`ConfirmedAnswerSegment`の不変データ型を追加する。
   - API／CLI manifest／Consoleで単一`roleplay_task`を互換変換し、複数設問を入力できるようにする。
   - 空集合、重複`prompt_id`、範囲外時刻、重複確定区間を検証する。

2. **時刻付きチャンクの共通前処理**
   - 既存ASRの出力を壊さず、`TranscriptSpan`を追加する。
   - VAD、チャンク、任意話者ターンの来歴をキャッシュキーに含める。
   - 同じ音声でASR／Sudachiの実行が一回だけである回帰テストを作る。

3. **候補回答セグメント**
   - 対話ターンと一人語りの保守的ルールを実装する。
   - `boundary_evidence`、`mapping_status=candidate`、設問順の候補を出す。
   - 意味埋め込み、LLM、設問内容の自動推論を追加しない。

4. **確認フロー**
   - API更新とConsole入力で、候補の結合・分割・設問選択・学習者話者指定を可能にする。
   - 確定履歴と元候補を保存する。
   - UIを追加する場合は、候補／確定を視覚的に区別し、未確定時はJudge開始を無効にする。

5. **回答Viewと5モジュール統合**
   - 確定済みの学習者回答Viewを一度生成する。
   - FluencyをFact Packet化して、5軸を同じRunnerから選択可能にする。
   - Interactionを追加する。各モジュールの独立実行をテストする。

6. **Judge／協議接続**
   - 確定した設問・回答単位だけをJudge入力にする。
   - 生音声を送らないこと、未確定・未提供能力を不利な根拠にしないことをプロンプトとテストで保証する。

7. **検証と回帰防止**
   - 既存4軸の固定fixtureで直列化済み出力を比較する。
   - 一人語り、設問音声なしの連続解答、面接対話、話者分離なし、未確定候補を網羅する。
   - APIとConsoleが同じオーケストレータを通ることを統合テストする。
   - 実装後にBug Hunterで、誤対応・未確定評価・話者混入を再現して検査する。
