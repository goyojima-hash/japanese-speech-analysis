# Fact-Module 既定全モジュール統一 回帰レポート

## 再現した挙動

`evaluate_speech_level(..., selected_modules=None)` は Fluency と Range だけを選択する一方、対話ターミナルは実装済みの事実モジュールすべてを選択していました。そのため通常の API 評価では、客観データと Judge 入力の両方から `accuracy_data` と `coherence_data` が欠けていました。

## 期待する挙動

モジュール部分集合を明示指定しない場合、両入口は同じ実装済み4モジュール（Fluency、Range、Accuracy、Coherence）を選択します。モジュール単独利用のための明示的な部分集合指定は維持します。

## 5 Whys

1. なぜ API は実装済み2パケットを省いたのか。既定定数が `fluency` と `range` だけを持っていたためです。
2. なぜターミナルと異なったのか。ターミナルは対応モジュール集合を明示指定し、API は既定値に依存していたためです。
3. なぜ共通 runner 導入後も差が残ったのか。runner は収集処理を統一したものの、古い応答互換性ポリシーを意図的に残していたためです。
4. なぜ今は不具合なのか。プロダクト方針が、両入口で既定時に実装済み全事実モジュールを使うことへ変わったためです。
5. なぜ再発しないのか。`DEFAULT_FACT_MODULES` は対応モジュール集合を直接参照し、テストが既定 API のパケットと Judge への伝播を検証するためです。

## フィッシュボーン対策

| 領域 | 対策 |
| --- | --- |
| ポリシー | `SUPPORTED_FACT_MODULES` を唯一の既定選択にする |
| 入口 | 両方とも異なる既定を持たず `run_fact_modules` を呼ぶ |
| 任意性 | 明示的な `selected_modules` 部分集合は検証付きで維持する |
| 契約 | API テストで Accuracy / Coherence の応答と Judge 入力を確認する |
| 文書 | 要件、設計、計画、現行フローに共通既定を記載する |

## タイムライン

1. runner と API の対象テストで異なる既定選択を再現しました。
2. 既定で全モジュールを選択し、パケットが伝播することを失敗するテストとして先に追加しました。
3. 共有既定定数のみを変更し、抽出アルゴリズムとパケット形式は変更しませんでした。
4. 共通 runner の仕様とフロー図を更新しました。
5. 対象テスト、全テスト、コンパイル、空白、図の描画を検証しました。

## 再発防止

API とターミナルに異なる暗黙のモジュール既定を与えません。新モジュールは一度だけ `SUPPORTED_FACT_MODULES` に登録し、選択省略時は両経路に含めます。部分的な事実だけが必要な呼び出し元だけが、明示的な部分集合を指定します。
