# 共通Evidence層統合レポート

## 問題

テスト先行で追加したEvidence層テストは、`jgrade_eval.evidence` が未作成だったため最初に失敗した。これは想定どおりのRed段階であり、修正中も維持すべき統合契約を示している。

## 再現手順

1. `uv run python -m unittest tests.test_evidence` を実行する。
2. `ModuleNotFoundError: No module named 'jgrade_eval.evidence'` を確認する。

## タイムライン

- 要件・設計・タスク・ADRを追加。
- Evidence層の集中テストを追加。
- パッケージ未作成の失敗を再現。
- Evidenceパッケージを追加。RangeとAPI統合後に集中テストを再実行する。
- 厳格なパイプラインにテストFakeが旧形式の辞書を直接渡した、フィクスチャ契約不一致を再現した。
- API統合時に、公開Evidenceパッケージが互換アダプターをexportしておらずimportに失敗した。
- 公開exportを追加し、モデル来歴でキャッシュキーが変わる回帰テストを加えた。全68テストの成功を確認した。

## 5 Whys

1. なぜテストが失敗したか。Evidenceパッケージをimportできなかった。
2. なぜimportできなかったか。テストを先に書いた時点ではパッケージが存在しなかった。
3. なぜ先にテストを書くか。実装前に、採点をしない安定した契約を固定するため。
4. なぜこの契約が重要か。選択可能な5モジュールが評価ロジックを共有せず、同じ事実を使う必要があるため。
5. なぜ記録するか。将来のリファクタリングでモジュールごとの重複抽出や採点を再導入しないため。

## フィッシュボーン

- コード: パッケージと統合点が新規。
- 依存関係: 現在はRangeがSudachiトークン化を所有している。
- データ: 現在のFluency出力はEvidenceに必要な一部の事実を破棄している。
- プロセス: 既存APIテストはEvidenceメソッドを持たない旧形式のFakeを使う。
- パッケージ公開: APIが利用する共通層の協調オブジェクトが公開一覧に含まれていなかった。

## 修正と再発防止

- API統合前にEvidenceパッケージと集中テストを整える。
- 旧形式のFluency／Range Fakeに対応するアダプターを維持する。
- 厳格なパイプライン境界では明示的なFluency互換アダプターを必須にし、テストもアダプターを通す。
- Rangeが一度のトークン化を再利用する回帰テストと、任意キャッシュ再利用テストを追加する。
- 完了前に集中テストと全テストを実行する。
- API が利用する共通層の公開シンボルは `jgrade_eval.evidence` から明示的に export し、API結合テストで検証する。
- この環境には `ruff` がない。プロジェクトのlint導入までは、コンパイル、全テスト、`git diff --check` を必須検証として維持する。
